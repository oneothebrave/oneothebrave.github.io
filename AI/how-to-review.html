AI Agent 时代的软件质量保障体系 ​

文章总结自：https://claude.dev/blog/solving-code-review-at-anthropic

前言 ​

如今，AI 生成的代码已经占了相当大的比重。而当AI生成的一个PR，代码有几百上千行时，当 Agent 生成代码的速度远高于人类阅读代码的速度时，该怎么进行Code Review呢？

要回答这个问题，我们从第一性原理的角度出发：Code Review是为了什么？

  1. 在代码交付前发现并修复问题

    例如逻辑错误，语法错误，安全漏洞等

  2. 在团队内部传播代码知识

    通过阅读别人的Diff，理解架构，业务逻辑和模块之间的依赖关系

对于第一点，AI review，自动化测试可以解决大部分工作。

对于第二点，如今可以让AI生成对特定模块，特定改动的解释，来更好地理解项目中发生的改动。

因此，Code Review的价值是值得保留的，只是形式有必要发生变化。

新的流程 ​

过去，CR发生在开发结束后，往main里合代码前。通常会让非作者之外的1-2个工程师进行人工审查。原文中有句话：

We think "did a human read the code?" is an imprecise proxy for "what could go wrong with this change, and which check—automated or human—is the right one to catch it?”

作者认为，人类有没有阅读过这段代码并不是衡量代码质量的准确标准。而是这次变更可能导致什么问题，应该用哪种自动化或者人工审查来发现它？

人类将只要专注于涉及钱（计费、支付）、安全（认证、权限、加密）、数据（迁移、删除、不可逆写入）、发布流程（CI、安装器、自动更新）这些方面，而没必要将注意力花费在语法、格式、类型错误、常见的低级 bug这些能由编译器、lint、测试和 AI 审查发现的地方

瑞士奶酪模型 ​

  • 每一层检查都像一片有洞的奶酪：AI reviewer 会漏掉某些 bug，测试覆盖不到某些路径，人也会看走眼；
  • 但各层的"洞"位置不同，一个问题要穿过所有层，需要每一层的洞刚好对齐；
  • 最后一层（回滚）不是用来兜底：漏过去的问题，影响要尽量小、修复要尽量快。

第一层：别人看之前先验证自己的工作 ​

这一层的核心观点是：

Agent不应该在“认为自己完成任务”时就结束工作，而应该在“有证据证明要求符合要求”之后才结束

假设你给了Agent这样一个任务：完成用户注册功能。Agent会按照读取代码 → 生成实现 → 完成 这样的流程工作，然后通知你任务完成。

但是LLM的本质是根据上下文预测下一个输出，并不能等价于实际执行验证。

因此，

完成用户注册功能

和

实现用户注册功能，并验证：

  • 有效邮箱能够成功注册。
  • 重复邮箱被拒绝。
  • 密码不符合要求时注册失败。
  • 注册完成后数据库存在正确记录。
  • 执行测试并展示结果。

是完全不同的。

怎么进行验证呢？

原文中提到：

a subagent reviews the diff with fresh context

即由一个拥有全新上下文的Subagent进行审查。

因为LLM是一个根据上下文预测下一个输出的模型，原Agent的上下文已经包含大量先前的推理，决策和解释。会影响后续的判断。

什么是 Fresh Context ？

  • 不继承writer agent的完整对话历史，推理过程，自我评价和未经验证的判断
  • 包含必要部分：任务需求，验收标准，相关代码，Git Diff, 项目约束等
  • 使用不同模型可能降低共同盲区，但不是必须的

文中还提到了两个重要文件：CLAUDE.md 和 REVIEW.md

  • CLAUDE.md : 定义项目与开发约束。

    告诉Agnet项目是什么，采用什么技术栈，遵循哪些规范，应该如何验证，哪些行为不能执行。

    由于该文件会经常被加载到上下文中，所以应当尽量保持简短。将广泛适用的规则保留在该文件中，将特定场景的工作流放到按需加载的 Skills 中

  • REVIEW.md : 定义审查标准。

    告诉 Reviewer 哪些缺陷最重要、什么构成真实问题、哪些路径可以忽略，以及需要什么证据才能报告问题。

    如果Reviewer不断发现相同类型的问题，应将可机械判断的规则写入 Linter、测试或 Hook；将语义约束写入 Skill 或指令文件

第二层：每个 PR 都有 AI review ​

这一层的核心观点是：

多个 Agent 同时找 bug，然后另一组 Agent 对每个发现投票，只有足够多的Agent 同意该问题确实存在时，它才会被提交

第一阶段，多个 Agent 同时分析： ​

  • PR 的变更内容（Diff）。
  • PR 声明的修改目标。
  • 变更涉及的上下游代码。
  • 仓库中的约束和约定。

尽可能找到值得调查的问题，主要在于扩大搜索范围，而非保证任何单个 Agent 的判断都正确。但是并行 Agent 越多，候选Bug通常也可能越多，其中就可能包含大量误报，还可能导致漏报。

因此需要另一组Agent投票。

第二阶段：投票 ​

多数投票的可靠性依赖 Agent 判断之间的独立程度，如果基于同一错误假设或者不完整的需求，那么增加 Agent 数量也未必有帮助

因此，工程上不应该只依赖投票，还应该尽量引入不同来源的证据，例如：

  • 实际的函数调用路径。
  • 项目已有的测试和不变量。
  • 具体的错误输入及预期行为。
  • 可执行的最小复现案例。

最终保留下来的审查发现会以严重程度排序

第3-7层：代码安全合并 ​

如何建立一套制度，让未经充分验证的高风险代码无法轻易进入生产环境，同时让低风险修改快速通过？

核心思想：

多层纵深防御

将代码交付设计为六层检查，加上最终的快速检测和回滚机制

前两层讲了PR前验证和AI Code Review。

第三层：安全审查 ​

为什么必须独立，为什么不能并入普通的Code Review？

举个例子：

python
@app.get("/users/{user_id}")
def get_user(user_id: int):
    return db.get_user(user_id)

从功能角度看，这个接口可能正确返回用户数据，但是功能测试全部通过，仍然不能证明接口安全。因为如果它缺乏必要的身份认证和对象级授权检查，其他用户可能通过修改 user_id 获取不属于自己的数据。

合法用户能否正确读取自己的数据 和 恶意用户能否读取其他人的数据 这两种测试的出发点是不同的

第四层：Automated CI ​

在 PR 创建之前，Coding Agent 已经进行了Lint、Type Check、多平台测试以及 Build，为什么CI还需要运行？

因为CI验证检查由预定义工作流控制，在受控测试环境中接受统一规定的测试集，而Agent本地验证的命令则由Agent决定，测试范围可能只涵盖了一部分，且本地与生产环境可能存在差异

第五层：人工审查 ​

原文给出了明确的三级风险体系。

风险等级典型变更人工审批要求
Low文档、文案、仅内部使用的功能、Feature Flag 后的新增功能自动检查通过后可无需人工审批
Medium普通产品变更、缓存、自动更新器、System Prompt1 人
High最高风险代码及指定的敏感路径2 人

第六层：合并检查 ​

假设主分支当前有两个 PR：

PR A 修改了函数 calculate_total() 的返回类型，PR B 修改了调用该函数的代码，但依赖旧的返回类型。

两者都是基于同一个旧版本的主分支开发的。它们各自通过 CI，并不能保证合并后的代码仍然通过 CI。

第七层：快速回滚 ​

无论 Reviewer 有多少层，测试覆盖多么充分，都无法保证完全消除生产环境中的 Bug。因此快速发现、快速回滚是非常重要的。例如 Feature Flag，可以在无需重新部署的情况下关闭有问题的新功能

熔断机制本身也符合整篇文章的思路，用确定性的规则来兜住其他环节的不确定性。分类器可能判断错风险，AI reviewer 可能漏掉 bug，但"指标超过阈值就收紧"是一条确定的规则，不依赖任何人的判断。

在文章中还有一个深层次的问题：

我们如何知道 Reviewer 本身是否可靠？当它出现漏报、误报，甚至陷入无限审查循环时，应该怎样系统性改进？

作者给出的方案是：

“Any incidents are now an eval.”

即将真实事故转化为评估案例的一部分。其核心目标是：

Reviewer 的升级不能只凭主观感觉，而需要通过可重复的真实案例验证。

理解并掌控系统 ​

如果说前面的主题主要回答如何让AI Agent 更可靠地发现和修复代码问题，那么这部分就要回答另一个关键问题：当 AI 能够完成绝大多数开发与审查工作时，人类工程师还有哪些不可替代的职责？

作者给出的答案是

将人类注意力集中到方向、架构、风险判断、证据解释与结果责任上。

文中列出了五类仍由工程师负责的工作。

第一类：决定是否应该开发 ​

假设你让 Agent 实现一个通知系统，Agent 可能提出这样的架构：

  • Redis 消息队列
  • 独立的通知微服务
  • WebSocket 服务
  • 定时重试任务
  • 统一事件总线

看着好像很健壮，代码可能也很完善，但是真正需要判断的是：

这个架构解决的复杂度，是否大于它本身引入的复杂度？

如果当前你的应用只有几百名用户，真的需要这样的架构吗？这种问题仍需要交给工程师思考，也就是原文中的话：

“should we even do this?”

第二类：审查高风险代码 ​

正如前文所说，对于计费、自动更新器、CI Workflow 等高风险代码，仍然需要人工参与。不过不是让工程师重新做一遍 AI 已经完成的所有审查，而是判断系统关键不变量是否被破坏

第三类：审查架构 ​

原文中强调：

“Reviewing architecture that sets a pattern others will copy.”

假设一个 Agent 设计了错误的数据库访问层，随后其他 Agent 都沿用这个设计，那么这个错误的设计就会被不断放大。因此，越是会被后续 Agent 复用的设计，越值得人类提前审查。

第四类：阅读验证证据，而不只是阅读 AI 的结论 ​

验证证据能够帮助工程师识别验证范围和残余风险，而Agent 提供的 “所有测试通过，功能已经完成，代码质量良好”只是模型对自己工作的总结。文章的要求可以概括为：

如果工程师无法解释自动化检查可能遗漏什么，就不应该仅凭 AI 的结论快速批准变更。

不再阅读所有 Diff，工程师如何理解代码库？ ​

核心思想：

从被动阅读所有变更，转向按需理解特定模块

当工程师需要理解某个模块时，可以让AI针对那部分代码生成解释，甚至还可以创建可视化工具辅助理解。

例如可以向AI提问：“解释这个项目的缓存生命周期，包括缓存创建、读取、失效、更新，以及相关模块之间的依赖关系。请引用具体的函数和代码位置。”

因此最重要的是阅读关键接口、调用路径和高风险实现，验证系统不变量，其他代码主要依赖自动化检查。同时应该允许 Agent 写出的代码被直接丢弃。

应用 ​

文章最后给出的建议并不是直接复制其内部多 Agent 架构，而是从现有项目开始，逐步增加验证、审查、风险控制和事故反馈机制

  • 先做成本最低的：写一份简短的 CLAUDE.md，PR 模板加上 Testing / Risk / How to revert，强制 CI；
  • 再引入 AI review：在一个仓库上启用 AI reviewer 和安全 review，用几周时间调 REVIEW.md；
  • 补上安全网：merge queue、feature flag、一键回滚。这是后面放宽人工审批的前提；
  • 开始记录指标：revert 率、incident 率、每个 PR 的人工 approve 数、等待时长；
  • 最后才放宽审批：有了安全网和数据之后，再逐步让低风险改动减少人工审批。
